## Authority and scope

Follow the authority order in `AGENTS.md`: official brief → AGENTS → SDD → this reference → approved decisions → implementation/tests → enhancement ideas. Existing code and passing tests cannot override a requirement. Do not treat historical coverage reports as current verification.

Required stack: PHP 8.2+ native OOP, MySQL 8, PDO prepared statements, Controller → Service → Repository, repository interfaces, manual constructor injection, HTML/custom CSS/Vanilla JS/Fetch, Docker Compose, PHPUnit and static analysis. No backend/frontend/CSS framework, admin template, ORM, CRUD generator, or framework DI container (brief pp. 12–13).

## Change protocol

Current UI component direction is documented in `docs/quality/design-system.md`: neutral workspace styling from the user-provided reference, implemented in custom CSS/Vanilla JS. Preserve full-viewport layout, shared styling, bottom Profile/logout, adjacent filters/table/pagination, and Export CSV in the header toolbar beside Create/Import when enhancing pages. Do not reintroduce redundant Home buttons or Search table.

Before each enhancement/fix, identify its requirement IDs and mandatory/optional classification. Read the relevant PDF section, SDD, code, schema, tests, and approved decisions. Determine actors/ownership, valid states, transaction boundary, affected invariants, and acceptance behavior. Preserve required role scope and state enums; never infer new requirements from UI ideas.

Stock changes must use the stock service: authorize and validate state; begin transaction; lock stock rows in deterministic order; validate after lock; mutate balance and append ledger; update source operation; commit or fully roll back. Follow AGENTS/ADR-002/003 for the implementation protocol. For fixes involving repeated/concurrent requests, also inspect whether source-order state and receipt remainder are validated against current transactional state. Stock locking alone is not proof that the same order cannot be processed twice.

Run relevant unit tests, real MySQL integration tests when persistence changes, and static analysis. UI changes need proportionate responsive/accessibility checks. Update actual evidence and AI disclosure; report only commands that ran. Docs-only changes do not require application regression tests. Follow the task report format in AGENTS.

Before optional work, verify the mandatory gate: requirements implemented, tests green, acceptable static analysis, clean Docker boot, and substantially complete evidence. The 2026-10-06 runtime check proves startup, login/dashboard/API smoke, unit tests, and static analysis; it does not establish the full optional-feature gate or current integration-suite status.

- Low stock / reorder point (10 October 2026, user decision D-10, ADR-016): one rule everywhere — active pair low when quantity < COALESCE(product_stocks.reorder_point_override, products.reorder_point); equal is not low. Products "Low stock" filter = low in any active warehouse. Admin-only, audited per-warehouse override on product detail; never a ledger movement. Use `ReorderThreshold`/`LowStockSql`, not new ad-hoc comparisons. D-05 trainer question still open.
- Order numbers (10 October 2026, user decision D-11, ADR-017): server-assigned `PO/SO-YYMM-NNNN` (UTC month of the DB clock that also sets order_date; counter per prefix/month, ≥4 digits). Claimed from `document_sequences` inside the draft-insert transaction; forms have no order-number input and services ignore any posted value. Never type or generate numbers elsewhere; tests that need a specific number use the repository directly. D-06 trainer question still open.
- Stock reservation (10 October 2026, user decision D-12, ADR-018): `product_stocks.reserved_quantity` (CHECK ≤ quantity); available = quantity − reserved. Approve reserves through `StockService::reserve()` (SO lock first, rows in product order, 422 when short, strict `sales-orders.approve` audit, no ledger); issue lowers quantity and reserved in one statement; cancelling an Approved SO releases; adjust/transfer/supplier return/unreserved issue never go below reserved. Low stock and replenishment use available via `LowStockSql`/`ReorderThreshold`. Invariant reserved = Σ Approved SO lines per pair (`StockReservationReconciler`); ledger reconciliation unchanged. Never write `reserved_quantity` outside StockService/the reconciler.
- Negotiated line prices (10 October 2026, user decision D-13, ADR-019, partially supersedes D-09/ADR-015): master price is the default and the server always snapshots it as `list_price`; a different PO/SO line price needs `price_reason` (3–255). SO never below current purchase price; Sales cap `SALES_MAX_DISCOUNT_PERCENT` (default 10), Admin uncapped; PO override > 0. Rules live in `OrderLinePricing`; never accept a client `list_price`. Detail pages show master/difference/reason and an approval/ordering notice. CHECK enforces reason ⇔ price ≠ list_price.
- Partial SO fulfilment (11 October 2026, user decision D-14, ADR-020; **new SO status `PartiallyFulfilled` outside the brief's status set**): `sales_order_items.issued_quantity` (CHECK ≤ quantity); issue takes per-line quantities 0..remaining (all-zero 422), one transaction per shipment (SO lock → replay hash over per-line quantities → rows in product order → one UPDATE lowering quantity and reserved per line → one Issue ledger row per line → issued/status → audit). Status Fulfilled when every line complete, else PartiallyFulfilled. Admin closes the remainder of a PartiallyFulfilled SO with a reason (`sales_order_closures`, releases the reservation, status unchanged, further issues 422); an Approved SO with nothing shipped must be cancelled instead; a PartiallyFulfilled SO cannot be cancelled. Reservation invariant: reserved = Σ(quantity − issued) of Approved/PartiallyFulfilled SO lines without closure (`StockReservationReconciler`). Outstanding SO quantity = Σ(ordered − issued) excluding closed; work queue and dashboard issue queue include open PartiallyFulfilled orders. Checks: `PartialFulfilmentChecks`.
- Transfers in transit (12 October 2026, user decision D-15, ADR-021; **operation-document statuses `Dispatched`/`Received` for transfers only**, brief PO/SO statuses and ledger movement set unchanged): PendingApproval → Approved → Dispatched → Received, cancel only before dispatch. Dispatch (Admin/Warehouse) locks the document then source rows, requires available (quantity − reserved) after the lock, quantity −= qty, negative TRANSFER Adjustment rows, `dispatched_quantity`, audit `inventory-operations.dispatch`; `post()` on a transfer = dispatch; repeats no-op. Receipt is single and complete: per line good + damaged ≤ dispatched, short = rest, reason mandatory for any write-off; good units enter the destination with positive Adjustment rows; damaged/short never become stock (no ledger row), audit `inventory-operations.receive`. Invariants (`TransferTransitChecks`): ledger per line = dispatched/received, status ⇔ line progress, Σ dispatched − Σ received − Σ damaged − Σ short = in transit, discrepancy has a reason. Read models: transfer detail, In Transit page, product detail in-transit inbound (never available), work queue TransferDispatch/TransferReceive, outstanding OP Dispatched, timeline, replenishment subtracts in-transit inbound. Migration `scripts/migrate-transit-transfer.php` (Posted → Received). Evidence `docs/testing/transit-transfer-2026-10-12.md`.
- Units of measure (12 October 2026, user decision D-16, ADR-022): **every stored quantity is in the product's base unit (smallest unit, factor 1, = `products.unit`)**; stock = ledger, reservations, partial fulfilment, transit, reorder points and replenishment all stay in base. Units live in `product_units` (one base unit, larger units with factor ≥ 2, optional unique barcode, own prices per unit else base × factor, at most one purchase/sales default). PO/SO/operation lines snapshot `unit_code`/`unit_factor`/`unit_quantity`; prices and the discount cap/cost floor are per entered unit (cost per unit = base purchase × factor); line total = unit_quantity × price; receipts/shipments are whole line units (CHECKs). Convert only at input (`UnitSet::toBase`, via `ProductUnitCatalog`) and display (`QuantityFormatter` / `order-items.js formatQuantity`). Admin-only `ProductUnitService`; code/factor immutable once used. Never multiply quantities outside `scripts/migrate-multi-unit.php`; checks: `MultiUnitChecks`. Availability API adds `base_unit`/`units` (existing fields base). Evidence `docs/testing/multi-unit-2026-10-12.md`.
- Batches, expiry and FEFO (12 October 2026, user decision D-17, ADR-023; no new PO/SO status or ledger movement type): **every unit belongs to a lot** (`stock_lots`: product + warehouse + code + expiry + unit cost per base unit); `product_stocks` stays the aggregate and the lock root (Σ lots = quantity, lot = opening + Σ ledger rows of the lot, every new ledger row has `lot_id`). Lock lots only after every pair of the operation, by point lookups on (pair, lot_seq) — never a range `FOR UPDATE` on lot tables (gap locks deadlock neighbouring pairs). Expired = expiry < today in `APP_TIMEZONE` (use `BusinessDate`/`ExpirySql`, never `CURRENT_DATE`); available = quantity − expired − reserved (`LowStockSql::available()`, `ProductStock::availableQuantity()`). Receipts split per line into lots (tracked products need expiry); issues and transfer dispatches allocate FEFO automatically over non-expired lots; returns use the original movement's lot; counts are per lot; expired stock leaves only through the Admin-approved `ExpiredWriteOff` adjustment. Over-reservation after expiry is refused at issue (422) and reported, never auto-cancelled. Read models: product lots, `/reports/expiry` (+CSV), dashboard card, `/lots` recall trace. Checks: `BatchLotChecks`; migration `scripts/migrate-batch-expiry.php [--dry-run]`. Evidence `docs/testing/batch-expiry-2026-10-12.md`.
- Barcodes and stock counts (12 October 2026, user decision D-18, ADR-024; count document statuses Draft/Counting/Submitted/RecountRequested/Approved/Posted/Cancelled, PO/SO statuses unchanged, ledger stays Receipt/Issue/Adjustment): `GET /api/barcodes/{code}` (Admin/Warehouse; Sales 403). Scanning (keyboard wedge + optional `BarcodeDetector`) only fills forms; the server stays authoritative; exact unit conversions only; no drafts of scan counts. Count variance = counted − (snapshot + Σ ledger rows of the lot between the snapshot and the count **ledger-id watermarks**, read under the pair locks); posting applies the approved variance as a delta to the **current** lot via `StockService::postCount()` — never set to counted; refusals list every conflicting line (422). Do not run non-locking reads before the stock locks in count transactions (REPEATABLE READ view). Only assigned counters count; recount by a different counter (CHECK); approval by an Admin who counted nothing; blind for counters/Warehouse; no two open counts of a warehouse share a product. Checks: `StockCountChecks`; migration `scripts/migrate-stock-counts.php [--dry-run]`. Evidence `docs/testing/barcode-stock-count-2026-10-12.md`.
- Price lists, quotations, delivery notes and invoices with PPN (12 October 2026, user decision D-19, ADR-025; quotation statuses Draft/Sent/Accepted/Rejected/Cancelled with **Expired computed from `valid_until`**, invoice state computed, PO/SO statuses and ledger movement types unchanged): `PriceResolver` = customer's active, valid list at the highest tier `min_quantity ≤` line unit quantity for exactly the product and unit, else master; `list_price` is now the **resolved** price (ADR-019 reason/cap measured against it; cost floor also on the tier; tier below cost refused). `SalesLineBuilder` prices SO and quotation lines; the server re-resolves on save (`GET /api/price-resolution` is display only). One live invoice per delivery note (lock note; `active_delivery_note_id` UNIQUE); payments under the invoice lock, no overpayment; void only without payments, never touches stock. - Inventory valuation FIFO per batch (12 October 2026, user decision D-20, ADR-026; no new status or ledger movement type): every lot keeps its unit cost per base unit; outbound quantities take the cost of the lot FEFO allocated (cost follows the physical lot). Every ledger row with a lot stores `unit_cost` and `cost_amount` = signed quantity × lot cost in whole cents (half away from zero, `CostAmount`; CHECK `chk_stock_ledger_cost`); `StockService` passes the locked lot's cost — never write ledger rows elsewhere. PPN − COGS, void invoices excluded, shipped-not-invoiced apart), `/reports/inventory-losses`, each with CSV; COGS/margin panels on SO, delivery note (no-print) and invoice pages.
