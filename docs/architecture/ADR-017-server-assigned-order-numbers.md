# ADR-017: server-assigned order numbers PO/SO-YYMM-NNNN

Date: 10 October 2026. Decision: project owner (user), D-11. Not a trainer decision and not an official brief requirement. Requirement support: PO-01, SO-01, DB-01, ARCH-01, ARCH-02, VAL-01. The D-06 trainer question (order-number format) stays open; this ADR is the implemented user default and points back to it.

**Context.** The brief requires each PO/SO to have an order number and the schema keeps it unique, but the format is not specified (D-06). The create forms had a required free-text `order_number` field prefilled with `PO-`/`SO-` + `date('YmdHis')`; users could type anything, two people opening the form in the same second got the same prefill (the second save failed with a unique-key error), and the demo data mixed two formats (`PO-2610-0002` from the seed, `PO-20261009141927` from manual practice). The user chose the seed format for all new orders.

**Decision.**
- **Format.** `PREFIX-YYMM-NNNN`: `PO` or `SO`, two-digit year and month, a counter per prefix per month starting at `0001`. The counter is zero-padded to at least four digits and simply grows after 9999 (`PO-2610-10000`, `PO-2610-123456`); nothing is truncated or wrapped. Formatting and parsing live in `App\Support\OrderNumber` (`format()`, `period()`, `parse()`).
- **Clock and time zone.** YYMM is the month of `CURRENT_DATE` on the MySQL session clock, the same clock that sets `order_date` in the draft insert. In this deployment that is UTC: the MySQL containers run with `time_zone = SYSTEM` (UTC), PHP has no `date.timezone` setting (UTC), and no application time-zone setting exists. Consequence: an order created between 00:00 and 06:59 WIB on the first of a month gets the previous month's YYMM, consistent with its `order_date`. Changing to WIB would mean setting the MySQL session time zone for both, which is out of scope.
- **Server-only.** The create forms no longer contain an `order_number` input; they show "Order number is assigned when the draft is saved (PO-YYMM-NNNN …)". Controllers do not read `order_number`, and `PurchaseOrderService::createDraft()` / `SalesOrderService::createDraft()` no longer accept it, so a tampered POST value is ignored (same approach as master prices in ADR-015). The detail page heading shows the assigned number as before.
- **Sequence table.** `document_sequences(prefix VARCHAR(10), period CHAR(4), last_number INT UNSIGNED, updated_at, PRIMARY KEY(prefix, period))` with CHECKs for prefix `PO`/`SO` and a four-digit period. The column is `last_number` because `LAST_VALUE` is a reserved word in MySQL 8.
- **Claim and transaction.** After authorization and validation (role, active party/warehouse, lines, master prices), the service opens one transaction through `StockService::transaction()` (shared `TransactionManagerInterface`). Inside it: `DocumentSequenceRepositoryInterface::currentPeriod()`, then `next(prefix, period)`, which runs `INSERT … VALUES (…, LAST_INSERT_ID(1)) ON DUPLICATE KEY UPDATE last_number = LAST_INSERT_ID(last_number + 1)`, then the PO/SO header and item inserts. The repository `createDraft()` now joins an active transaction (via `MySqlTransactionManager::run()`) and only opens its own when called alone. `next()` refuses to run outside a transaction.
- **Concurrency.** The upsert takes an exclusive lock on the `(prefix, period)` row until commit, so concurrent creates of the same prefix and month queue; PO and SO, and different months, do not block each other. The lock is held only for the draft inserts (no stock rows are locked by draft creation), so lock order cannot deadlock with stock workflows.
- **Gaps.** None from failures: a failed draft (for example a unique-key or FK error on insert) rolls back its claim together with the order rows, and the next draft reuses the value. Rejected input and forbidden roles fail before the transaction and never touch the counter. Gaps would only come from deleting orders, which the application does not support.
- **Duplicates.** Never. The counter is the source; `UNIQUE(order_number)` stays the final guard. If someone inserts a number in the generated pattern outside the application, the next create for that period fails with 422 "A record with that unique value already exists." (claim rolled back) until the migration is re-run, which raises the counter past the foreign number.
- **Other creation paths.** Only `PurchaseOrderService::createDraft()` and `SalesOrderService::createDraft()` (HTTP controllers) create orders. CSV import covers master data only. `scripts/generate-fmcg-seed.php` and `tests/Support/large-dataset.php` now call the same services without a number; the generator's `SET TIMESTAMP` moves the session clock, so each seed order's YYMM follows its historical date. Repository-level `createDraft($number, …)` remains a persistence method for tests and fixtures.

**Migration.** `database/migrations/20261010-order-number-sequences.sql`, run by `scripts/migrate-order-number-sequences.php` (schema version `order-number-1`). Additive and idempotent: creates the table if missing, then for each prefix/period takes the highest counter among numbers matching `^PO-[0-9]{4}-[0-9]{4,10}$` / `^SO-…` (case-insensitive, matching the column collation, so `po-2610-0040` also counts) and raises the counter to it with `GREATEST`, never lowering it. Non-matching legacy numbers (`PO-20261009141927`, `PO-2610-018`, suffixes) are ignored and stay unchanged; they cannot collide because generated numbers always have the exact pattern. The runner fails if any exact-pattern number is above its counter. The readiness probe now resolves `document_sequences`, so run the migration before activating the new image.

**Seed.** Rebuilt once with `python3 scripts/build-fmcg-seed.py`. All 1,000 seed order numbers and every other seed row are byte-identical to the previous seed; the dump adds 14 `document_sequences` rows equal to the per-month maximum (PO-2610 = 18, SO-2610 = 38).

**Consequences.** Users can no longer choose or mistype a number, and two simultaneous creates no longer collide. Numbers are predictable per month, which is acceptable for internal documents. Draft creation of the same prefix is serialized for the few milliseconds of the insert. Existing tests that posted or asserted typed numbers were changed to the server-assigned format.

**Tests.** `OrderNumberTest` (format, growth beyond 9999, period and time zone, parse, invalid parts, in-memory counters, services continue after existing maximum, new month restarts at 0001, forbidden/invalid creates do not claim), `PurchaseOrderServiceTest`/`SalesOrderServiceTest` (assigned number, rejected input not consumed), controller tests (posted `order_number` ignored, form has no input), `OrderNumberIntegrationTest` (seed counters = max, continues after the current maximum, tampered number ignored through the MySQL-backed controllers, rollback reuses the value, claim requires a transaction, failed draft rolls back its claim and the unique key guards, migration initialization and idempotency, 6 parallel processes × 8 drafts give unique consecutive numbers). Evidence: `docs/testing/order-number-2026-10-10.md`.

Note 12 October 2026 (D-19, ADR-025, user decision): the same sequence table and format number quotations (`QT`), delivery notes (`DO`) and invoices (`INV`); the prefix CHECK was widened to PO, SO, QT, DO, INV. Each is claimed inside its document's transaction (delivery notes inside the shipment transaction, after the stock locks).
