# ADR-016: one low-stock rule and per-warehouse reorder point

Date: 10 October 2026. Decision: project owner (user), D-10. Not a trainer decision and not an official brief requirement. Requirement support: PRD-01, WH-01, FIND-01, DASH-01, JOB-01, DB-01, ARCH-01. Supersedes the "product-level reorder points apply equally to warehouses" note of D-05. The D-05 trainer question (meaning of low stock across warehouses) stays open; this ADR keeps its per-warehouse default.

**Context.** Dashboard, `scripts/check-low-stock.php` and replenishment already counted active product/warehouse pairs with `quantity < products.reorder_point`. Two places disagreed: `ProductStock::isLowStock()` (Low badges on the product list and detail) used `<=`, and the Products "Low stock" filter compared the *total* across warehouses with `<=`. A product low in one warehouse but high in total was shown as Low in its badge, yet not found by the filter. The user also wanted a warehouse to be able to keep its own buffer (for example the central Cikarang hub).

**Decision.**
- **One rule.** A pair is low when the product and the warehouse are active and `quantity < effective_reorder_point`. Equal is not low. `effective_reorder_point = COALESCE(product_stocks.reorder_point_override, products.reorder_point)`.
- **Where it lives.** `App\Support\ReorderThreshold` (PHP) and `App\Repository\MySql\LowStockSql` (the same expression for SQL). Users: `ProductStock::isLowStock()` and `effectiveReorderPoint()`, Products filter (`MySqlProductRepository::whereClause`), Admin dashboard count and Warehouse low-stock rows (`MySqlOperationalQueryRepository`), the low-stock command, and replenishment (`MySqlBusinessOperationRepository::recommendationSql`). The Sales dashboard has no low-stock data (brief p. 7) and stays unchanged; the work queue and reports have no low-stock usage.
- **Products filter.** "Low stock" = low in at least one active warehouse (`EXISTS`); "Normal" = low in none (`NOT EXISTS`). Every active product is in exactly one of the two.
- **Override.** `product_stocks.reorder_point_override INT UNSIGNED NULL`, with `CHECK (reorder_point_override IS NULL OR reorder_point_override >= 0)`. Null = use the product default. 0 = never low in that warehouse.
- **Replenishment.** Suggested = `max(0, effective − stock − open PO supply)`; closed-remainder POs still do not count as supply (ADR-009/013).
- **Who.** Admin only, enforced in `ReorderPointService::assertCanManage()/setOverride()` (403 for Sales and Warehouse Staff, checked before input parsing). The controller (`POST /products/reorder-point`) only parses HTTP input.
- **Validation.** Empty clears the override; otherwise digits only, 0 to 4,294,967,295 (the column range). Invalid input returns 422 on the product detail page with the attempted value kept; nothing is saved.
- **Transaction and audit.** One transaction: lock the pair (`SELECT … FOR UPDATE`), update the override, append `audit_logs` action `products.reorder-point` (entity `products`, product id, metadata `warehouse_id`, `previous_override`, `override`, `product_reorder_point`, `effective_reorder_point`). An audit failure rolls back the change. Saving the same value is a no-op without an audit row. The request audit recorder skips the success path (the service already records it) and still records failures. Quantity is never touched and no ledger row is written: a threshold is not a stock movement.
- **UI.** Product detail, "Stock by Warehouse": columns Reorder Point (effective) and Source ("Warehouse override" or "Product default") for every role; Admin also gets a small number form per warehouse (empty = product default). Inactive product or warehouse rows show an "Inactive" badge instead of Low/Normal. The summary label is now "Default Reorder Point". The command prints `reorder=<effective>` and adds ` (warehouse override)` when an override applies. Replenishment marks overridden thresholds with "warehouse".

**Schema/migration.** DDL in `database/schema-and-seed.sql` (schema version `reorder-override-1`). Existing databases: back up, then `php scripts/migrate-reorder-point-override.php` from the new image (`database/migrations/20261010-reorder-point-override.sql`, idempotent via `information_schema` checks). The readiness probe now resolves the new column, so run the migration before activating the new image.

**Seed.** The generator sets 15 overrides through the service after the document history (10 fast movers in Gudang Pusat Cikarang at 2 × default; 5 slow movers in Gudang Regional Makassar at ½ × default), so all documents, stock and ledger rows are unchanged. Low-stock pairs stay 22.

**Consequences.** Badges, filter, dashboard, command and replenishment now agree. Some products formerly "Low" by total (`total <= reorder`) or by badge equality (`quantity == reorder`) are now Normal, and products low in one warehouse are now found by the filter. Products list "Reorder" column and sort still show the product default; per-warehouse values are on the detail page. Product-level CSV import/edit are unchanged.

**Tests.** `ReorderThresholdTest` (effective rule, `<` boundary, inactive rows, input parsing), `ReorderPointServiceTest` (Admin OK with audit, Sales/Warehouse 403, no-op, 404, 422, controller and read-only view, in-memory filter), `ReorderPointOverrideIntegrationTest` (MySQL dashboard count, Products filter per warehouse, replenishment with override and open PO, command output, atomic audit rollback, migration repeat), plus updated `MySqlMasterDataCoverageIntegrationTest`, `MySqlOperationalQueryCoverageIntegrationTest` and `DemoSeedIntegrationTest`.

Note 12 October 2026 (D-16, ADR-022, user decision): reorder points and overrides are stored in base units (the migration multiplied converted products by their factor); product detail shows them with the unit breakdown.

Note 12 October 2026 (D-17, ADR-023, user decision): low stock compares available = quantity − expired lots − reserved; the single rule is now `LowStockSql::available()` / `isLow()` (methods, because the expiry date is computed from the business clock).
