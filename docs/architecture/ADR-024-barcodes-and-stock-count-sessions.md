# ADR-024: barcode scanning and stock count sessions

Date: 12 October 2026. Decision: project owner (user), D-18, approved with Series 2 on 2026-10-11 (feature #3). **Not a trainer decision and not an official brief requirement.** No PO or SO status changes and no new ledger movement type: count corrections are `Adjustment` rows (reference `STOCK_COUNT`). The count document has its own statuses (user decision, recorded in D-18). Requirement support: PRD-01, WH-01, PO-01, SO-01, REPORT-01, API-01, VAL-01, DB-01, AUTH-01/02, ARCH-01/02, UI-01, TEST-01/02/03. Builds on ADR-009 (adjustments, independent approval, baseline 409), ADR-014 (form drafts), ADR-018 (reservation), ADR-020 (partial shipments), ADR-021 (transit), ADR-022 (units and barcodes in `product_units`) and ADR-023 (lots, FEFO, lock order). Their invariants are unchanged.

## Part 1 — barcode lookup and scanning

- **Lookup.** `GET /api/barcodes/{code}` (`BarcodeController` → `BarcodeService` → `ProductUnitRepositoryInterface::findByBarcode()`). Returns the product (id, SKU, name, active, base unit, tracks expiry), the unit (code, factor to base, base flag, active) and `usable` (product and unit active). Conventions of the availability API: JSON body, `{"error": …}`, **401** without a session, **403** for Sales (scanning serves receiving, picking and counting — warehouse tasks; checked in the service before the input is parsed), **404** unknown code, **422** malformed code. Validation (`BarcodeService::normalize()`, mirrored in JS): 4–64 letters, digits or dashes (the stored alphabet of ADR-022); a 13-digit code must carry a valid EAN-13 check digit, so a misread digit is reported instead of resolving to another product. The router gained generic one-segment placeholders (`/api/barcodes/{code}`).
- **Scan component** (`public/assets/js/barcode-scan.js`, `views/partials/barcode-scanner.php`). Primary input: USB/Bluetooth **keyboard-wedge** scanners, which type into the focused field and press Enter. The field has no name, sits outside every form and Enter is prevented, so a scan never submits a form; scans are processed one after another. The result is announced in a polite `aria-live` status region (success/warning/error tone) and dispatched as `barcodescan` / `barcodeerror` events. **Camera:** a "Scan with camera" button appears only when `BarcodeDetector` and `getUserMedia` exist; errors (permission, missing camera) fall back to a message — Safari/iOS never see the button.
- **Exact conversions only.** A scanned unit is applied to a line when its factor is a whole multiple of the line unit's factor (a karton of 24 on a pcs line adds 24; a box of 12 on a karton-24 line is refused with a message: "1 box (12 pcs) is not a whole karton (24 pcs) …"). Rejected alternative: carrying fractional remainders — receipts and shipments are whole line units (ADR-022).
- **Receiving** (PO detail): each line's receive form carries product, unit factor, unit and remaining units; a scan increments the matching line's quantity by one line unit. Unknown barcodes, products not on the PO, inactive units and scans beyond the remaining quantity show a visible error and change nothing. Lots are entered per line exactly as before (ADR-023); the user still presses **Receive** per line, and the server validates everything again.
- **Picking** (SO detail): "Start scan to pick" sets the issue quantities to 0 and counts scans per line in the line unit; issue quantities follow the picked counts (capped at the remaining quantity). Wrong products are flagged and never counted; over-picks are counted with a warning ("put N back"). The server remains authoritative: FEFO lot allocation, availability, expiry and reservation (ADR-018/020/023).
- **Drafts (ADR-014) — decision: scan counts are not drafted.** The PO receive and SO issue forms never had drafts (they carry idempotency keys) and a picked count must reflect what is physically in hand now, not a count restored hours later. Count sheets save counts on the server (**Save Counts**), so nothing lives only in the browser. The scan field has no name, so `form-drafts.js` never stores it; draft forms are unaffected (browser acceptance 20/20).

## Part 2 — stock count sessions

### Model

- `stock_counts`: warehouse, scope (`All`, `Category` + category, `Products` + `stock_count_products`), status, reason, created/started/submitted/recount/approved/posted/cancelled stamps, `snapshot_ledger_id`, `recount_round`.
- `stock_count_counters`: assigned counters (Admin or WarehouseStaff accounts).
- `stock_count_products`: the selection of a `Products` count and, at start, the materialized scope of every count.
- `stock_count_lines`: one per lot with stock at the snapshot (`Snapshot`) or entered as found (`Found`): snapshot quantity, counted quantity (base; the entered unit and unit quantity are kept), counter, time and **count watermark**, expected quantity, recount fields (the same set), generated `variance`, `approved_variance`, and the posting result (lot, delta, unit cost, pair quantity after, reservation at posting).
- **Statuses** (count document statuses, user decision): Draft → Counting → Submitted → (RecountRequested → Counting → Submitted) → Approved → Posted; Cancelled any time before posting. Recording a recount moves RecountRequested back to Counting.
- **DB guards** (CHECKs): category scope ⇔ category; started counts have a snapshot watermark and starter; Approved/Posted have approval stamps; Posted ⇔ posting stamps; Cancelled ⇔ cancellation stamps and reason; count and recount field sets all-or-nothing; a recount needs a first count and a flag; **recounter ≠ counter**; approved variance = variance; posted delta = approved variance; pair quantity after posting ≥ reservation at posting; snapshot lines always have a lot; a lot-less (new found) line has snapshot 0. `stock_lots.source_type` now also allows `STOCK_COUNT` (found lot created by a count).

### Variance with stock moving during the count (core design)

Stock keeps moving between the snapshot, the count and the posting. Ordering uses **ledger ids, not timestamps**:

1. **Start** (Admin): lock the count, then every pair of the scope in product order and their lots (ADR-023 order), check that no other open count of the warehouse shares a product (409), read the ledger watermark `W0 = MAX(stock_ledger.id)` and verify every locked lot against the ledger at W0 (lot = opening + Σ rows ≤ W0), then store one line per lot with stock, snapshot = locked lot quantity.
2. **Count / recount** (assigned counter): lock the count and its lines, then the pairs of the counted lines and their lots; read the watermark `Wc` under these locks; `expected = snapshot + Σ ledger rows of the lot with W0 < id ≤ Wc`, cross-checked against the locked lot quantity; `variance = counted − expected`.
3. **Posting** (after approval): `StockService::postCount()` locks the count, the pairs (product order) and lots, re-verifies every line's expected value from the ledger, and applies **delta = approved variance to the current lot quantity**: movements after the count are kept, the count is never "set to counted".

Why the watermark is exact: every movement of a lot runs while its pair row is locked (StockService). While a count holds the pair lock, no transaction can be writing a row of that lot; every earlier row is committed and visible, and every later row is inserted after the lock is released and therefore receives an auto-increment id greater than any id visible now. InnoDB fixes the REPEATABLE READ view at the first consistent read, so these transactions perform only locking reads before the stock locks (the scope is resolved before the transaction; the count rows are read `FOR UPDATE` without joins, so a count lock never touches product, lot or user rows out of order); the ledger and watermark reads come after the locks. The start and the count verify lot = ledger at their watermark, so a violated assumption fails loudly instead of producing a wrong variance. Remaining real-world gap (documented, not solvable in software): goods moved physically between the moment the shelf was counted and the moment the count is saved; counters save per shelf, and locations being counted should not be picked meanwhile.

**One discrepancy is corrected once.** Two open counts of a warehouse cannot share a product (checked under the pair locks at start), and posting refuses with 409 when another count posted a `STOCK_COUNT` correction on a line's lot after that line was counted. ADR-009 count adjustments keep their baseline check (409 when a count session changed the lot meanwhile); an ADR-009 adjustment posted during an open session is treated like any other movement.

### Posting refusals

Before anything changes, every line is checked after the locks; **all** conflicts are listed in one 422 ("Posting refused; nothing was changed. Conflicting lines: line #… SKU lot …: …"): a delta that would make a lot negative, overflow, leave the pair below its reservation (ADR-018) or leave less non-expired stock than reserved (ADR-023), or a found lot of a tracked product without expiry. Otherwise one `Adjustment` ledger row per lot with a non-zero delta (reference `STOCK_COUNT`, count id), the pair moves by the net delta, the lines record lot, delta, unit cost, pair quantity after and the reservation, and the strict audit row `stock-counts.post` commits in the same transaction. Repeating a posting is a no-op.

### Recount and approval

- **Tolerance**: a line is within tolerance when |variance| ≤ max(`COUNT_RECOUNT_TOLERANCE_UNITS`, ⌊expected × `COUNT_RECOUNT_TOLERANCE_PERCENT` / 100⌋); defaults 0 units and 2 %, out-of-range values fall back to the defaults. A reviewer (Admin) may request a recount only for lines above the tolerance, **once per line**, with a reason, optionally assigning extra counters.
- **Different counter — enforced** (choice): the first counter of a line cannot recount it (422 in the service, CHECK in the database); a recount request is refused unless at least one assigned counter differs from each flagged line's counter. The recount replaces the first count (its own watermark and expected value); both stay visible to reviewers.
- **Independent approval** (mirrors ADR-009): an Admin who counted or recounted any line of the count cannot approve it (403). The creator may approve (creating the scope produces no numbers). Approval freezes `approved_variance` per line.
- **Found lots**: during the first count a counter may enter a lot of an in-scope product that is not on the sheet. An existing lot without stock at the snapshot becomes a line whose snapshot is worked back from the ledger (current − movements since W0); an unknown lot (code, expiry required for tracked products) has snapshot and expected 0 and is created at posting with cost = the product's current purchase price per base (ADR-023 cost rule) and source `STOCK_COUNT`.

### Authorization (services)

Admin creates, starts, requests recounts, approves (independently) and cancels. Only the **assigned counters** count or recount (choice over "all Warehouse": the assignment is the accountability record and makes the recounter rule enforceable). Admin and WarehouseStaff see counts and post approved counts. Sales gets 403 on every count page, report and the barcode API.

**Blind count**: assigned counters and WarehouseStaff never receive snapshot, expected, variance or value while a count is Counting, Submitted or RecountRequested — the service omits them, the page cannot leak them; a line flagged for recount also hides its first count. Reviewers (Admins who are not counters of the count) see everything. Product pages still show stock to warehouse users; blindness covers the count sheet.

### UI, reports, work queue

`/stock-counts` (list, filters, "Assigned to me"), `/stock-counts/create`, `/stock-counts/show` (summary, scan panel, counting sheet with manual entry in any active unit, found-lot form, review table with snapshot/expected/counted/variance/unit cost/value impact and tolerance badges, recount request, approve, post, cancel). `/reports/stock-counts` (history and variance summary of posted counts: units gained/lost/net, value at lot cost) and `/reports/stock-counts.csv` (formula-safe; numbers stay numbers). Count adjustments appear in Stock Movements (reference `STOCK_COUNT`) and the lot trace ("Stock count #n variance"). Work queue: **Count to do** (assigned counter), **Count to review** (Admin who did not count), **Count to post** (Admin/Warehouse). Successful count POSTs are audited by the service (`stock-counts.*`), not by the request recorder.

## Migration

`database/migrations/20261012-stock-counts.sql` (additive, idempotent: four tables; the lot source CHECK is replaced by a superset only when it lacks `STOCK_COUNT`) and `scripts/migrate-stock-counts.php [--dry-run]`, which verifies tables, constraint, `StockCountChecks` and `BatchLotChecks` before recording `stock-count-1`. No existing row changes; re-running is a no-op that re-verifies.

## Consequences

Barcodes speed up receiving, picking and counting without trusting the browser. Counts are blind, recounted by someone else, approved independently and posted as deltas, so concurrent movements are never lost and a discrepancy is never corrected twice. Costs: counts lock every pair of their scope briefly at start; one recount per line; a recount needs a second assigned counter; the found-lot cost is the current purchase price; overlapping open counts of a warehouse are refused; scan state of receive/pick is not kept across reloads; the camera path is Chromium-only.
