# ADR-020: partial sales order fulfilment with the PartiallyFulfilled status

Date: 11 October 2026. Decision: project owner (user), D-14. **Not a trainer decision and not an official brief requirement.** The brief's SO status set is Draft → PendingApproval → Approved → Fulfilled (+ Cancelled). This ADR deliberately adds a sixth status, `PartiallyFulfilled`, because the user chose it on 2026-10-11 (Series 2, feature #4). Requirement support: SO-01, DASH-01, REPORT-01, DB-01, ARCH-01, ARCH-02, TEST-01/02. Builds on ADR-004 (source order lock first), ADR-008 (replay), ADR-009 (PO close-remainder, customer returns), ADR-010 (work queue), ADR-012 (outstanding), ADR-018 (reservation) and ADR-019 (line prices, unchanged).

**Context.** Issue was all-or-nothing: an Approved order shipped every line at once or stayed Approved. Distributors routinely ship what is on the truck and deliver the rest later; the remainder must stay visible and its stock must stay protected (ADR-018).

**Decision.**
- **Schema.** `sales_order_items.issued_quantity INT UNSIGNED NOT NULL DEFAULT 0` with `CHECK (issued_quantity <= quantity)`; `sales_orders.status` ENUM gains `PartiallyFulfilled` (between Approved and Fulfilled); new table `sales_order_closures (sales_order_id PK, closed_by, reason VARCHAR(500), closed_units > 0, created_at)` following `purchase_order_closures`. Remaining per line = quantity − issued_quantity.
- **Why a status, not Approved + a flag.** The user asked for an explicit status so lists, filters, badges, dashboards and reports show partially shipped orders without extra columns. Recorded as a user decision outside the brief (D-14); the trainer may still prefer staying inside the brief's set.
- **Issue = one shipment (mirrors the PO receipt).** `SalesOrderService::issue(actor, id, key, quantitiesByItemId)`. Warehouse/Admin only (403 before any lock). Payload checks first: negative → 422, all zero / empty → 422 ("Enter an issue quantity above zero for at least one line"). One transaction: lock the SO (`FOR UPDATE`) → replay check (ADR-008; the SHA-256 fingerprint covers operation, order id and the sorted non-zero per-line quantities, exactly like PO receipts, so a replay with the same key never issues twice and a different payload with the same key is 409) → closure check (422 when the remainder is closed) → status must be Approved or PartiallyFulfilled → every item must belong to the order and qty ≤ remaining (422) → `StockService::issue(..., releaseReservation: true)` locks the stock rows in product order, re-checks `quantity ≥ qty` and `reserved_quantity ≥ qty` **after the lock**, lowers both in **one** `UPDATE` per line (ADR-018 CHECK semantics) and appends one Issue ledger row per line → `recordIssue()` adds `issued_quantity` (the `UPDATE … WHERE issued_quantity + q <= quantity` and the CHECK are database guards) and sets Fulfilled when every line is complete, otherwise PartiallyFulfilled → strict audit `sales-orders.issue` with `movement_count`, `reservation_released_units`, `shipment_units`, `remaining_units`, `status_after` and `shipment` [{product_id, quantity}].
- **No quantities = every remaining unit.** Trusted callers (seed, fixtures) and a POST without `quantities` issue all remaining units; the replay hash is then the empty payload, as before this ADR, so in-flight legacy forms still replay correctly. The detail form always posts per-line quantities (prefilled with the remaining quantity).
- **Close remaining fulfilment (mirror of ADR-009 PO close-remainder).** `SalesOrderService::closeRemaining(actor, id, reason)`: Admin only, reason 1–500 characters (same validator as ADR-009). One transaction: lock the SO; already closed → 422; Approved → 422 (**chosen option: forbid**; nothing was shipped, so the existing cancel, which already releases the reservation, is the right operation); anything but PartiallyFulfilled → 422. `StockService::release()` locks the rows in product order, lowers `reserved_quantity` by each line's remainder, stores the closure row (`closed_units` = remainder) and writes the strict audit row `sales-orders.close-remainder` {reason, closed_units, reservation_released_units, reservation[]}. No ledger row (nothing moves). The status stays PartiallyFulfilled because goods were shipped; issued quantities and ledger rows stay. Later issues are refused with 422.
- **Cancel.** Cancelling a PartiallyFulfilled order is refused with 422 ("close the remaining fulfilment instead"): goods have left the warehouse, and a cancellation must not hide that. Cancelling an Approved order still releases its (whole, since issued = 0) reservation as in ADR-018.
- **Reservation invariant (updates ADR-018).** Per pair: `reserved_quantity = Σ (quantity − issued_quantity)` of the lines of Approved and PartiallyFulfilled sales orders from that warehouse whose remainder is not closed. `StockReservationReconciler::EXPECTED` uses this formula; on a database without `issued_quantity`/`sales_order_closures` it falls back to the D-12 formula, so the earlier stock-reservation runner still works when migrations are applied in order.
- **New invariants** (`PartialFulfilmentChecks`): per SO line `issued_quantity = Σ Issue ledger rows` (reference SO, product, source warehouse); Fulfilled ⇔ every line complete, PartiallyFulfilled ⇒ something issued and something left, other statuses ⇒ nothing issued; closures only on PartiallyFulfilled orders with `closed_units` = remainder.
- **Lock order.** Unchanged: source order first, then stock rows in product order (ADR-004). Two concurrent shipments of one order serialize on the SO lock; the second recomputes the remainder from the locked row. An issue racing a closure also serializes on the SO lock; whichever is second sees the new state and is refused.
- **Read models.**
  - SO detail: Ordered / Issued / Remaining columns; an "Issue Now" number input per open line (min 0, max remaining, prefilled) only for Warehouse/Admin when the status allows and the remainder is open; a "Fulfilment" summary ("Issued X of Y units"); "Stock Reservation" shows the remainder held, "Released at issue", or "Released at closure (N units)"; Shipment History groups the Issue ledger rows (same time and performer, consecutive, a repeated product starts a new shipment — `ShipmentHistory`), visible to everyone who may view the order, with the customer-return link per Issue row for Warehouse/Admin; closure info (who, when, reason, released units); "Close Remaining Fulfilment" reason dialog for Admin; Cancel is hidden for PartiallyFulfilled.
  - Lists/filters/badges/reports: `PartiallyFulfilled` is a filter option and a warning-tone badge (`status-partially-fulfilled`); Order Status report counts it (not as completed). The Sales "Open Orders" metric includes it.
  - Outstanding report (updates ADR-012): PartiallyFulfilled is open in the Admin, Warehouse and Sales scopes unless its remainder is closed; SO outstanding quantity = Σ (ordered − issued); `DaysSinceApproval` is shown for Approved and PartiallyFulfilled.
  - Work queue (updates ADR-010) and Warehouse dashboard: the issue task / `so_issue_queue` include PartiallyFulfilled orders without a closure ("Issue remaining goods"); Sales follow-up includes them too.
  - Timeline: the `sales-orders.issue` audit row is now shown as "Goods issued (shipment)" with "Shipped N units; M units still to ship" (older rows: "Shipped N units"); the closure appears as "SO remaining fulfilment closed" with its reason and released units; per-line Issue ledger rows stay.
  - Customer returns (ADR-009) are unchanged: they reference one Issue ledger row and are bounded by that row's quantity through `inventory_return_totals`; with several shipments an order simply has more Issue rows.
- **Readiness probe** resolves `sales_order_items.issued_quantity` and `sales_order_closures`, so run the migration before activating the new image.

**Migration.** `database/migrations/20261011-partial-fulfilment.sql` (idempotent: ENUM extension, column, backfill `issued_quantity = quantity` for Fulfilled orders keeping `updated_at`, CHECK, closures table) run by `scripts/migrate-partial-fulfilment.php`. The runner verifies the columns, then `PartialFulfilmentChecks`; if any count is non-zero it prints the counts, exits 2 and does not record schema version `partial-fulfilment-1` (fail with a report, as ADR-018). Then it re-runs the reservation reconciliation with the new formula (a no-op on consistent data, conflict report otherwise) and records the version. Stock quantities, ledger, prices and statuses are never changed.

**Seed.** About one approved order in four (chosen from the order id, no extra `mt_rand` call) ships in 2–3 shipments: 45–75 % of each open line, the last line waiting on the first shipment, the final shipment issuing the rest. Shipments after the end of the window do not happen, so recent split orders stay PartiallyFulfilled open; split orders with `id % 7 = 3` have their remainder closed by Admin with an Indonesian reason instead of the last shipment. Rebuilt once: 600 SO (Draft 4, PendingApproval 8, Approved 7, PartiallyFulfilled 25 of which 20 closed, Fulfilled 519, Cancelled 37), 700 shipments, 136 split orders, 119 orders with more than one shipment time, 96 partially issued lines, 20 closures. Summary: `ledger_mismatches 0`, `negative_stock 0`, `reservation_mismatches 0` (new formula), `reserved_above_quantity 0`, `issued_ledger_mismatches 0`, `fulfilment_status_mismatches 0`, `closure_mismatches 0`, `order_numbers_off_pattern 0`, `order_number_duplicates 0`, `sequence_mismatches 0`, `price_override_without_reason 0`, `so_lines_below_purchase_price 0`, `sales_discount_above_cap 0`. The document history differs from the previous seed because stock now leaves in parts.

**Consequences.** Partial shipments and backorders are visible and their stock stays protected; abandoned remainders are closed explicitly with a reason. One status outside the brief (documented, D-14). Shipment grouping on the detail page is a display heuristic over the ledger (two shipments of different products by the same user in the same second would show as one; the ledger rows and audit rows remain exact). No backorder dates, no partial reservation of a short line at approval (approval still needs the full quantity, ADR-018), no reopening of a closed remainder.

HTTP: `tests/HTTP/end-to-end.py` and `tests/HTTP/business-enhancements.py` partial-shipment scenarios. Evidence: `docs/testing/partial-fulfilment-2026-10-11.md`.
