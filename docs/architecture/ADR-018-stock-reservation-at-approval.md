# ADR-018: stock reservation at sales order approval

Date: 10 October 2026. Decision: project owner (user), D-12. Not a trainer decision and not an official brief requirement. Requirement support: SO-01, PRD-01, WH-01, DASH-01, JOB-01, API-01, DB-01, ARCH-01, ARCH-02, TEST-01/02. The official SO status set is unchanged (no new status). Builds on ADR-002 (row locks), ADR-003 (ledger), ADR-004 (source order lock first), ADR-006 (complete zero pairs), ADR-008 (replay), ADR-009 (stock operations), ADR-016 (single low-stock rule). Resolves the "Stock Reservation" deferral of SDD 22.1 and the "no reservation" limitation noted in ADR-009/ADR-013.

**Context.** Approval did not touch stock. Issue locked the order, then the stock rows, and checked quantity after the lock. Two Approved orders could therefore promise the same units, and the later issue failed; the SO detail page could only warn "Short N" (informational). Adjustments, transfers and supplier returns could also take stock that an Approved order was counting on.

**Decision.**
- **Model.** `product_stocks.reserved_quantity INT UNSIGNED NOT NULL DEFAULT 0` and `CONSTRAINT chk_product_stocks_reserved_lte_quantity CHECK (reserved_quantity <= quantity)`. Available = quantity − reserved_quantity. `quantity` keeps its meaning: physical stock, equal to the ledger sum.
- **Why a counter column, not a reservation table.** A reservation is fully determined by an Approved order's lines and source warehouse, so a separate table would duplicate `sales_order_items`. The counter on the already-locked stock row makes the check-and-reserve a single row-locked step and lets every decrease guard compare against it without a join. Traceability comes from the strict audit rows and the derived invariant below.
- **CHECK semantics.** MySQL 8.0.16+ enforces CHECK per row after each statement. The issue path therefore lowers `quantity` and `reserved_quantity` in **one** `UPDATE` (`issueReserved()`), never in two statements (`quantity` first would transiently break the CHECK). Unsigned arithmetic below zero raises error 1690, a second guard. Services check everything first, so these database guards only catch bugs.
- **Approve (PendingApproval → Approved).** Admin only (D-03 unchanged; 403 before any stock read). One transaction: lock the SO (`FOR UPDATE`), then `StockService::reserve()` locks the source rows in product-ID order, requires available ≥ quantity for **every** line (otherwise `ValidationException` 422 "Insufficient available stock at the source warehouse (…). Nothing was reserved." and nothing changes), adds to `reserved_quantity`, marks the SO Approved, and appends the strict audit row `sales-orders.approve` (entity `SO`) with metadata `warehouse_id`, `reserved_units`, `reservation` [{product_id, quantity}]. No ledger row: nothing moved. An audit failure rolls back the reservation and the status.
- **Issue (Approved → Fulfilled).** Unchanged order: lock SO → idempotency claim (ADR-008) → lock rows → post-lock check, now `quantity ≥ qty` **and** `reserved ≥ qty` → one `UPDATE` lowering both → Issue ledger rows → Fulfilled → audit `sales-orders.issue` with `reservation_released_units`. A completed replay returns before any stock work, so a reservation is never released twice.
- **Cancel.** `rejectOrCancel()` of an Approved SO releases its lines (`StockService::release()`) in the same transaction; Draft/PendingApproval cancellation releases nothing. Both write the strict audit row `sales-orders.cancel` with `previous_status` and `reservation_released_units`. Cancelling an already Cancelled order stays a no-op. Rejection (`OrderExceptionService::reject`) only applies to PendingApproval, which holds no reservation. A missing reservation on release is an invariant breach: `LogicException`, full rollback.
- **Every other decrease respects reservations.** `StockService::adjust()` (adjustment counts, transfer out, supplier return) refuses with 422 when `quantity + delta < reserved_quantity`, after the row lock; an unreserved `StockService::issue()` call requires available ≥ quantity. Increases (receipts, transfer in, customer return, positive adjustment) are unaffected. A physical count below the reservation therefore cannot be posted until an Approved order is cancelled or stock arrives; this is deliberate (the shortfall must be resolved explicitly).
- **Lock order.** Source document first (SO or inventory operation, ADR-004), then stock rows. Approval and issue touch one warehouse in product order; `adjust()` sorts by (product, warehouse). A product-ordered single-warehouse set is a subsequence of that global order, so no cycle is possible.
- **Audit success path.** Approve and cancel success is now recorded by the service in the transaction; `RequestAuditRecorder` skips `/sales-orders/approve` and `/sales-orders/cancel` on success and still records failures (same pattern as receive/issue).
- **Read models.**
  - SO detail "Available at Source": available, plus the order's own reservation when it is Approved (its own units are part of `reserved_quantity` but belong to it); an Approved order can therefore never show "Short". A "Stock Reservation" summary shows Reserved N units / Not reserved yet / Released at issue / Released at cancellation. The warning now says approval is refused until stock is available.
  - Product detail: Quantity, Reserved, Available per warehouse and in the summary; product list adds "N reserved, M available" when reserved > 0.
  - API `/api/products/{sku}/availability`: adds `total_reserved`, `total_available`, and per warehouse `reserved_quantity`, `available_quantity`; existing fields unchanged.
  - Timeline: "SO approved" shows "Reserved N units at the source warehouse" (from the approval audit), "SO cancelled" shows "Released reservation of N units".
  - Draft check (`/drafts/check`) reports available instead of physical.
- **Low stock and replenishment use available.** Reserved stock is committed, so it cannot cover the reorder buffer. The single rule of ADR-016 changes in one place: `LowStockSql::AVAILABLE` / `IS_LOW` and `ReorderThreshold::isLow(available, …)` via `ProductStock::isLowStock()`. Badges, Products filter, both dashboards, `scripts/check-low-stock.php` (appends `| reserved=R | available=A`, earlier fields unchanged) and replenishment (`suggested = max(0, effective − available − open PO supply)`; the page column is now "Available" with on-hand/reserved hint) follow.
- **Reports and ledger.** Unchanged: reconciliation stays `quantity = Σ ledger`. New invariant: for every pair, `reserved_quantity = Σ quantity of Approved SO lines from that warehouse` (`StockReservationReconciler::MISMATCHES`), checked by the seed summary and integration tests.

**Migration policy (existing data).** `database/migrations/20261010-stock-reservation.sql` (idempotent DDL: column, then CHECK; with every value 0 the CHECK always holds) and `scripts/migrate-stock-reservation.php`, which runs `StockReservationReconciler::reconcile()` in one transaction (locks Approved SOs, then all stock rows). Policy (a), **fail with a report**: if any pair would need more than its physical quantity (an Approved order that was already short, or a missing pair), nothing is reserved, the runner prints the pairs with SKU, warehouse, quantity, required and order numbers, exits 2 and does not record schema version `stock-reservation-1`. It never clamps and never changes orders; the owner resolves the listed orders (receive stock or cancel) and runs it again. Re-running after success is a no-op (`updated_pairs: 0`) and also repairs drift. Policy (b), reserve up to available and flag the rest, was rejected because it would weaken the invariant to "reserved ≤ Σ approved", and Approved would no longer guarantee issue. The readiness probe now selects `reserved_quantity`, so run the migration before activating the new image.

**Seed.** The generator now picks SO lines from available stock, counts approvals refused for shortage (`approve_short`, stays PendingApproval) and no longer writes request-style audit rows for approve/cancel (the service writes them). Rebuilt once; the document history differs from the previous seed because approvals now reserve. Summary: 600 SO (Approved 7, PendingApproval 4, Fulfilled 532, Cancelled 51, Draft 6), `approve_short: 0`, `issue_skipped: 0`, `ledger_mismatches: 0`, `negative_stock: 0`, `reservation_mismatches: 0`, `reserved_above_quantity: 0`, 45 reserved pairs / 600 units, `low_stock_pairs: 34` (available rule; 34 with the physical rule too). ADR-017's note that seed order numbers are byte-identical to the earlier seed no longer holds for this rebuild (the format and counters still match, `sequence_mismatches: 0`).

**Consequences.** Approved now means "goods held", and the oversell guard fires at approval instead of at issue (the competing-orders test now fails the second approval). A long-open Approved order blocks its units for other orders and for decreases until issued or cancelled; there is no expiry. Approval cost grows by one row lock per line. Physical counts below reservations cannot be posted until resolved. No in-transit, partial reservation, backorder or expiry semantics.

**Tests.** `StockReservationTest` (unit: reserve, short approval with nothing changed, other reservations, Admin only, issue release, replay, cancel/reject, missing reservation rollback, unreserved issue, adjustment/transfer/supplier return guards, ProductStock available/low, SO detail availability and reservation text, controller 422). `StockReservationIntegrationTest` (MySQL: seed invariant, lifecycle with audit metadata and ledger, short approval, cancel release with timeline, approval audit failure rollback, decrease guards via BusinessOperationService, DB CHECK and unsigned guard, low stock/replenishment/command/API/product read model, migration conflict report then success and repeat, reconciler drift repair). `ParallelStockIntegrationTest` (real processes: two approvals competing for the same stock, one wins; approval racing a transfer-out, available never negative). Updated tests are listed in `docs/testing/stock-reservation-2026-10-10.md`.

Note 11 October 2026 (D-14, ADR-020, user decision): issue may now release the reservation in several shipments, and closing the remainder of a PartiallyFulfilled order releases the rest. The reservation invariant becomes reserved = Σ(quantity − issued_quantity) of Approved and PartiallyFulfilled SO lines without a closed remainder.

Note 12 October 2026 (D-16, ADR-022, user decision): reservations, availability and every guard are in the product's base unit; an order line in karton reserves unit_quantity × factor base units.

Note 12 October 2026 (D-17, ADR-023, user decision): reservations stay on the aggregate, but approval requires available without expired lots, and an issue is refused (422) when a reservation outgrew the non-expired stock after lots expired; such pairs are listed in the Expiry report and nothing is cancelled automatically. Decreases also keep non-expired stock ≥ reserved.
