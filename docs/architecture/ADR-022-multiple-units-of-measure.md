# ADR-022: multiple units of measure with conversion (base unit = smallest unit)

Date: 12 October 2026. Decision: project owner (user), D-16, approved with Series 2 on 2026-10-11 (feature #1). **Not a trainer decision and not an official brief requirement.** No PO, SO or operation status changes and no new ledger movement type. Requirement support: PRD-01, PO-01, SO-01, WH-01, VIEW-01, API-01, VAL-01, DB-01, ARCH-01, ARCH-02, TEST-01/02. Builds on ADR-002/003 (locks, ledger), ADR-006 (catalog initialization), ADR-009 (stock operations), ADR-013/016 (replenishment, reorder points), ADR-018 (reservation), ADR-019 (negotiated prices), ADR-020 (partial fulfilment) and ADR-021 (transit). Their invariants are unchanged; they now hold in base units.

**Context.** A distributor buys in cartons and sells in cartons, boxes or pieces. Until now every product had one free-text `unit` (in the seed "karton") and every quantity was in that unit, so a minimarket buying 5 pieces could not be recorded, and nothing related a karton to its pieces.

**Decision.**
- **Base unit = smallest unit.** Every stored stock quantity is an integer in the product's base unit: `product_stocks.quantity/reserved_quantity/reorder_point_override`, `products.reorder_point`, `stock_ledger.quantity/quantity_delta`, PO/SO line `quantity/received_quantity/issued_quantity`, stock-operation line `quantity/baseline/dispatched/received/damaged/short`, `inventory_return_totals.returned_quantity` and `sales_order_closures.closed_units`. Conversion happens only at input (unit quantity × factor, `UnitSet::toBase()`, refused above the INT UNSIGNED range) and display. Stock = ledger, reserved = Σ open SO remainders, issued = Σ Issue rows, the transit equation and low stock keep their formulas and are simply in base units. Rejected alternative: decimal quantities in a "main" unit — they would bring rounding into the ledger and every invariant.
- **Units table.** `product_units (id, product_id, unit_code VARCHAR(30), factor_to_base INT UNSIGNED, barcode VARCHAR(64) NULL UNIQUE, purchase_price/selling_price DECIMAL(14,2) NULL, is_base, is_purchase_default, is_sales_default, is_active)`. `unit_code` is 30 characters, not 20, to match `products.unit` so the migration never truncates an existing unit. `UNIQUE(product_id, unit_code)`; exactly one base unit and at most one default per purpose are enforced by UNIQUE keys on generated columns (`IF(flag = 1, 1, NULL)`), so the database refuses a second base or default even outside the service. CHECKs: the base has factor 1 and every other unit factor ≥ 2 (a second factor-1 unit would only be an alias of the base); the base is always active and has no own prices; an inactive unit is never a default; prices ≥ 0. Without a purpose default the base unit is used.
- **Prices per unit.** A unit's own price is its master price per that unit. Without one, the master price is base price × factor, computed in whole cents (exact; no rounding happens there). `products.unit`, `purchase_price` and `selling_price` stay the base unit and its prices (chosen over deprecating them), so dashboards, inventory value (Σ quantity × base purchase price), CSV import/export, product list and search keep working unchanged. Product create inserts the base unit row in the same transaction; renaming `products.unit` renames the base row (a clash with another unit code of the product is a 422 from the UNIQUE key). Existing line snapshots keep the code they were entered with.
- **Order lines.** PO and SO lines store `unit_code`, `unit_factor` (snapshot) and `unit_quantity` as entered; `quantity` = unit_quantity × unit_factor (CHECK). `purchase_price`/`selling_price` and `list_price` (ADR-019) are per entered unit, so line total = unit_quantity × price (detail pages show it; the Sales dashboard value uses it). `OrderLinePricing` takes the unit: the master snapshot is the unit's master price; the Sales discount cap compares per unit; the below-cost rule compares with cost per unit = **base purchase price × factor** (not the unit's own purchase price, so a karton bought cheaper in bulk can never hide a below-cost piece price). An empty unit means the base unit, so older clients and fixtures that post base quantities keep working. Unknown or inactive units are a 422.
- **Receipts and shipments** (PO receive, SO issue with partial fulfilment) are entered as whole line units and converted with the line's frozen factor (`remainingUnitQuantity()`); CHECKs `MOD(received_quantity, unit_factor) = 0` and `MOD(issued_quantity, unit_factor) = 0` guard it. Rejected alternative: receiving loose pieces of a karton line, which would leave a fractional remainder in the line unit. The idempotency hash (ADR-008) covers the submitted line-unit quantities; the factor of a line never changes, so a replay maps to the same base quantities.
- **Stock operations** (adjustment, transfer, supplier/customer return) accept a unit per line and store base plus the snapshot. A count is entered in one unit (count in pieces for loose stock). Transfer receipt good/damaged quantities stay in base units (damage is counted in pieces) and the form names the base unit. Return lines use a unit of the original movement's product (the source endpoint returns its units) and are bounded in base units by the original ledger row.
- **Display.** One shared formatter, `App\Support\QuantityFormatter` (PHP) mirrored by `formatQuantity()` in `public/assets/js/order-items.js`: greedy over the active units, largest first, always with the base total: "101 pcs", "2 karton (96 pcs)", "2 karton + 5 pcs (101 pcs)". Used on product list and detail, PO/SO detail (line unit and base equivalent, per-unit price, line total), stock-operation detail and the order form's "= …" hint. Quantity inputs on detail pages name their unit.
- **Replenishment** stays in base: `suggested = max(0, effective − available − open PO supply − in transit)` (ADR-013/016/018/021). The page shows it as whole purchase-default units rounded up (`UnitSet::unitsCovering()`, e.g. 130 pcs → 3 karton) with the base quantity and the need, and prefills the PO with that unit (`pick[]=productId:units:unit`, single link `unit_code=`).
- **API.** `/api/products/{sku}/availability` adds `base_unit` and `units[{unit, factor_to_base, barcode, is_base, is_purchase_default, is_sales_default}]`. Existing fields keep their names and stay in base units (backward compatible for clients that ignore the new fields; for converted products the numbers are now pieces).
- **Admin management** on product detail (`POST /products/units`, `POST /products/units/update`): add, edit, deactivate/reactivate, set defaults, barcode (letters/digits/dashes; a 13-digit code must have a valid EAN-13 check digit), prices per unit. `ProductUnitService` checks Admin first (403 for Sales/Warehouse before any input is parsed), validates, then in one transaction locks the product's unit rows (`FOR UPDATE`), clears the previous default of a purpose before setting the new one, writes and appends the strict audit row `products.units` (change, unit and previous values). The request audit recorder skips the success path, as for other service-audited routes.
- **Factor immutability.** Once any PO/SO line or stock-operation line has snapshotted a unit code, that unit's code and factor can no longer change (422 "deactivate it and add a new unit instead"). Lines are self-consistent through their snapshot, but a silently changed factor would make the product's unit list disagree with what people ordered and received, and reports grouped by unit would mix two meanings of "karton". Deactivating keeps history readable; barcode, prices and defaults stay editable.
- **CSV import.** Product import keeps its columns; `unit` becomes the base unit (factor 1). A separate unit import was not added (units are added on the product page); documented as a gap.

**Concurrency.** Stock workflows are unchanged: units only change the arithmetic before `StockService` is called, and every lock, post-lock check and ledger row is in base units, so no new stock race exists and the existing real-process tests (`ParallelStockIntegrationTest`) still cover the stock paths. The only new shared state is `product_units`. Two Admins editing one product's units serialize on the `FOR UPDATE` of its unit rows, with the UNIQUE keys as the final guard. A factor change racing a document that uses the unit: the document transaction share-locks the used unit rows (`FOR SHARE`, `ProductUnitCatalog::confirmSnapshots()`) and re-checks factor and status; the unit edit locks the rows `FOR UPDATE` and then checks usage. Whichever is second either waits and sees the new line as "used" (factor change refused) or sees the changed factor (document refused with "reload"). Unit rows are locked only by draft/proposal creation (after the order-number row, ADR-017) and by unit edits, never by stock workflows, so no lock cycle is possible. A dedicated parallel test was therefore not added; the race is closed by the lock pair above and the snapshot keeps every line correct even in the worst case.

**Migration (existing data).** Phase A `database/migrations/20261012-multi-unit.sql` (additive: table, nullable line columns). Data step `App\Repository\MySql\MultiUnitMigration` in **one transaction** (lock products and stock rows; products whose name ends with "(N pcs)" or "(N pak)", N ≥ 2 and unit ≠ that word, as the seed generator writes them, get base `pcs`/`pak`; the old unit becomes a unit with factor N that keeps the old master prices as own prices and is the purchase and sales default; `products` prices become `ROUND(old / N, 2)` (MySQL DECIMAL rounding, half away from zero); every historical quantity of the product × N; lines get the snapshot (old unit, N, old quantity), so line prices and Rupiah totals do not change; closures are recomputed from their lines; other products keep their unit as base, factor 1, lines (unit, 1, quantity)). Before commit it re-checks every invariant (stock = ledger, reservations, fulfilment, closures, transit, sequences, price reasons, unit checks), that the stock value Σ quantity × base purchase price differs by at most Σ converted base quantity × Rp 0,005 (rounding of the derived base price), and that **every PO/SO line total is unchanged**; any failure rolls everything back and the runner exits 2 without recording `multi-unit-1`. Phase B `20261012-multi-unit-finalize.sql` makes the columns NOT NULL and adds the CHECKs. `scripts/migrate-multi-unit.php --dry-run` prints the report first without changing anything (products and factors, products kept as base, rows to multiply, overflow check, invariants, projected stock value, line totals). Re-running after success is a no-op that re-verifies. Audit metadata written earlier keeps the numbers of its time (history is never rewritten). Forms opened before the migration and submitted after it would post base quantities without a unit, so the app is stopped during the migration.

**Seed.** Products get pcs (or pak for diapers by the bal) as base, karton/bal with own prices as purchase and sales default, plus box (12) or renceng (10) where the carton size allows; every unit has an EAN-13-like barcode with a valid check digit (prefix 899). Base selling prices carry a 5 % retail premium over the carton price per piece. POs are in cartons; wholesale outlets buy cartons, minimarkets and shops buy pieces or boxes, supermarkets mix; transfers move whole cartons where possible. Summary adds `line_unit_mismatches`, `whole_unit_mismatches`, `base_unit_mismatches`, `line_list_price_mismatches` (master-priced lines equal their unit's master price), `barcode_check_digit_errors`, all 0, besides every earlier check.

**Consequences.** Cartons, boxes and pieces can be bought, sold, moved and counted without fractional stock; all invariants keep one unit per product. Numbers in the API, reports and CSV exports of converted products are now pieces. Derived base prices are rounded to cents. No fractional units, no per-customer unit prices, no unit-level stock, no unit import, no conversion of historical audit metadata.

Note 12 October 2026 (D-17, ADR-023, user decision): lot quantities are in base units and a lot unit cost is per base unit (line price ÷ unit factor, whole cents). `MultiUnitMigration` also scales existing lots when it runs on a database that already has them.

Note 12 October 2026 (D-19, ADR-025, user decision): price list tiers are per unit (matched exactly against the line unit); delivery notes and invoices show the line unit and base quantity.
