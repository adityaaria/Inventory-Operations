# ADR-026: inventory valuation FIFO per batch, COGS and gross margin

Date: 12 October 2026. Decision: project owner (user), D-20, approved with Series 2 on 2026-10-11 (feature #7, "inventory valuation FIFO per batch"). **Not a trainer decision and not an official brief requirement.** No PO, SO or operation status changes and no new ledger movement type (Receipt, Issue, Adjustment stay the brief's set). Requirement support: DASH-01, REPORT-01, DB-01, VAL-01, SEC/AUTH-01, ARCH-01, ARCH-02, TEST-01/02. Builds on ADR-002/003 (row locks, ledger as source of truth), ADR-019 (negotiated prices), ADR-021 (transit, write-offs), ADR-022 (base units, cents rounding), ADR-023 (lots: unit cost per base, cost in the lot identity, `LEGACY` lots at purchase price, migration watermark), ADR-024 (count adjustments) and ADR-025 (delivery notes, invoices, PPN). Their invariants are unchanged.

## Context

The dashboard showed "inventory value" as on-hand quantity × today's master purchase price. When suppliers change prices, that figure is neither what the stock cost nor what was sold, and the business could not tell its cost of goods sold (HPP) or gross margin. Since ADR-023 every unit already belongs to a lot with a fixed unit cost; the ledger only lacked the cost of each movement.

## Decision

### Costing method: FIFO per batch = specific identification of the lot

- Every lot keeps its fixed `unit_cost` per base unit (ADR-023, `DECIMAL(14,2)`; the cost is part of the lot identity, so a receipt at a new price is a new cost layer and layers are never averaged).
- Every outbound quantity takes the cost of the lot it physically left. The lots are chosen by the existing allocation (ADR-023: FEFO — expiry ascending, no expiry last, then first receipt, then id); valuation does not choose lots itself.
- **Why FEFO and not receipt-date FIFO.** For perishable goods the physical flow is "first expired, first out": shipping a later-received lot that expires sooner is the correct warehouse practice and is what the system already enforces. Costing a different lot than the one shipped (pure receipt-date FIFO) would make the books disagree with the goods: a lot could show quantity 0 while still holding value, and lot recalls, transfers, write-offs and the per-lot roll-forward below would no longer reconcile. So cost follows the physical lot (specific identification at lot level). For products without expiry FEFO degenerates to receipt order, i.e. classic FIFO. This is what "FIFO per batch" means here.

### Cost on every movement

- `stock_ledger.unit_cost DECIMAL(14,2)` and `stock_ledger.cost_amount DECIMAL(24,2)` (24 digits hold INT UNSIGNED quantity × the largest `DECIMAL(14,2)` cost without overflow).
- **cost_amount = signed quantity × lot unit cost**: Receipt +, Issue −, Adjustment = the sign of `quantity_delta` (transfer out −, transfer in +, write-off −, count ±, returns ±). **Precision and rounding: whole cents per row, half up on the absolute value (half away from zero)**, so a movement and its exact reversal always cancel (`App\Support\CostAmount`, integer arithmetic only). Because lot costs have two decimals, the product is always whole cents today and no rounding actually happens; the rule only decides a cost given with more decimals.
- `StockService` passes the locked lot's cost with every ledger row (receipt, FEFO issue, adjustment/return/write-off, transfer dispatch and receipt, count posting); the MySQL repository falls back to the lot's own cost if a caller passes none. The row is written inside the same transaction and pair/lot locks as before (ADR-002/023), so no new lock or race exists: concurrency only decides *which* lot a movement takes, never what it costs.
- **DB guard** `chk_stock_ledger_cost`: a row has a cost exactly when it has a lot, the cost is ≥ 0 and `cost_amount = signed quantity × unit_cost`.
- **Transfers carry their cost** (ADR-021/023): the out rows are valued at the source lot cost, the destination lot has the same code, expiry and cost (identity), so the in rows carry the same cost; damaged and short units have no ledger row and are recognised as a **transit loss** = units × the lot cost recorded on `inventory_operation_lots`.
- **Valuation start = the ADR-023 migration watermark.** Ledger rows up to `stock_lot_watermark.legacy_ledger_max_id` have no lot and get **no cost**; reports show them as "before valuation start" and never invent a cost. The opening value is the `LEGACY` lots' `opening_quantity × unit_cost` (stage D: current purchase price at the lot migration). The start time is the later of the watermark row's time and the last pre-watermark row. A fresh install (watermark 0) values all history.

### Invariants (`App\Repository\MySql\ValuationChecks`, all 0)

`ledger_cost_missing`, `ledger_cost_without_lot`, `ledger_cost_lot_mismatches` (row cost = its lot's cost; row product/warehouse = the lot's), `ledger_cost_amount_mismatches`, **`lot_value_rollforward_mismatches`** (per lot: quantity × cost = opening × cost + Σ cost_amount, to the cent), **`pair_value_mismatches`** (per product/warehouse: Σ lot values = Σ opening values + Σ valued rows of the pair), `transit_cost_mismatches` (transfer lot rows carry the source lot's cost; destination lots the same; out rows = −dispatched × cost; in rows = received × cost), **`transit_value_mismatches`** (per transfer: dispatched value = received value + loss value + value still in transit), **`cogs_delivery_note_mismatches`** (COGS of a delivery note = −Σ cost_amount of its linked Issue rows = Σ its lot rows × lot cost, ADR-025) and `cogs_order_mismatches` (per SO: Issue COGS = Σ COGS of its delivery notes). The value of a warehouse/product is defined as Σ lot values, which the pair check ties to the ledger.

### Read models (Admin only)

All cost and margin read models are Admin only: `InventoryValuationService` refuses Sales and Warehouse with 403 before parsing input; the controller only asks for costing panels when the viewer is Admin. Warehouse keeps seeing lot unit costs where ADR-023/024 already show them (product lots, expiry report, count review) but has no valuation, margin or loss report. Business dates use `APP_TIMEZONE` (a day ends at midnight there, converted to UTC for the ledger).

- **Dashboard card "Inventory Value"** (Admin) = lots at cost on hand + in transit at lot cost, linked to the valuation report. **Decision on the old figure:** kept on the card as a labelled reference, "on hand at today's master purchase price" — it is a replacement-cost estimate, useful to see price drift, but not the inventory value.
- **Inventory valuation** `/reports/valuation` (+ `.csv`): current or **as of a date** (value at the end of that business day = current value − Σ cost_amount of rows written since; refused with 422 before the valuation start and for future dates), grouped by warehouse, category, product or lot, filters warehouse/category/search, plus the **in transit** list (units dispatched not yet received or written off, at their lot cost) and the total on hand + in transit.
- **Reconciliation** `/reports/valuation-reconciliation` (+ `.csv`): per warehouse for a period of business dates: opening + receipts + transfers in + issues (COGS, negative) + transfers out (negative) + adjustments and returns + count variances + expired write-offs = closing, plus an **In transit** line (opening transit + value dispatched − value received − transit losses = closing transit) and a **Total** line. Opening and closing are computed independently from the lot values rolled back by the ledger, so the Difference column is a real check; it must be 0 everywhere. A period that starts before the valuation start opens at the valuation start (stated on the page; unvalued rows are counted). Transfers in of shipments dispatched before the valuation start have no transit counterpart and are shown as transfers in.
- **Gross margin** `/reports/gross-margin` (+ `.csv`): per invoice line, customer or product for invoices dated in the period, **void invoices excluded**: net revenue (invoice line amounts, i.e. the subtotal excluding PPN, ADR-025) − COGS of the lots the invoiced delivery-note line shipped = gross margin and %. Lines shipped before the valuation start have no COGS: their revenue is shown apart and never enters the margin. Shipments without a live invoice are listed separately as **shipped not invoiced** (COGS and SO value for reference, no revenue).
- **Losses** `/reports/inventory-losses` (+ `.csv`): expired write-offs (ADR-023, valued rows), transit damage and shortage (ADR-021, units × transfer lot cost) and negative count variances (ADR-024), by kind and in total.
- **SO, delivery note and invoice detail** show COGS (lots × unit cost) and margin to Admin only; on the printable surat jalan the panel is `no-print`.

## Migration

Additive. Phase A `database/migrations/20261012-inventory-valuation.sql` (columns + `idx_stock_ledger_created`), then `App\Repository\MySql\InventoryValuationMigration` in **one transaction**: lock every stock pair (no movement can run), give every ledger row that has a lot its lot's `unit_cost` and `cost_amount`, re-check every valuation and lot invariant plus stock = ledger; any failure rolls back and exits 2 without recording the version. Phase B `20261012-inventory-valuation-finalize.sql` adds the CHECK; the runner `scripts/migrate-inventory-valuation.php [--dry-run]` then records `inventory-valuation-1`. The dry run prints the rows to backfill per movement with their cost, the lot value now, the LEGACY opening value and the projected roll-forward difference (must be 0). Re-running is a no-op. From phase B on, the previous image cannot write ledger rows, so the new image is started right after. `MultiUnitMigration` now refuses to rescale products that already have valued rows (unit conversion must precede valuation).

On 8080 (12 October 2026): backup first; dry run: watermark 6,421, 6 rows to backfill (2 PO receipts +Rp 50.979,15, 4 SO issues −Rp 1.319.974,98), projected difference 0; apply: ready, 6 rows backfilled, every check 0; re-run no-op. Valuation Rp 37.361.047.031,37 = LEGACY opening value Rp 37.362.316.027,20 + later movements −Rp 1.268.995,83.

## Seed

Costs were already on lots; to create realistic cost layers, principals send **price letters** over time: from June +3 % (supplier id % 3 = 0) or +1.5 % (id % 3 = 1), from August a further +2.5 % (even ids), a −2 % July promotion (id % 5 = 1). PO lines are priced at the letter (negotiated price with the letter as reason, ADR-019); the master purchase price stays the catalogue price (the cost floor and price lists keep referring to it). The generator makes no extra random draw, so the document history is identical to the D-19 build. Rebuilt once: 1,395 PO lines at letter prices, 828 cost layers, 262 products with several costs; on hand Rp 37.148.783.671,44 + in transit Rp 52.171.633,08; invoiced net revenue Rp 7.052.550.650,00 − COGS Rp 6.146.652.538,91 = gross margin Rp 905.898.111,09 (12.8 %); every month April–October reconciles to the cent and chains to the next; every valuation and earlier invariant 0 (evidence file).

## Consequences

Inventory value and COGS now come from the actual cost of the batches that moved, transit and losses are valued, and every figure reconciles to the cent with the ledger. Costs: two columns per ledger row and one CHECK; reports read the ledger (an index on `created_at` supports period queries); history before the valuation start stays unvalued (on 8080: everything before the lot migration); the master-price figure is only a reference; landed costs (freight, duties), standard costing, revaluation/write-down to net realisable value, credit notes and returns netted against margin, and inter-company transfer pricing are out of scope.
